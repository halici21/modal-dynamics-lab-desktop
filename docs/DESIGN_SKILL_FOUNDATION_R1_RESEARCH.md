All eight repositories named in the brief were reached; none were inaccessible.

## 2. Project baseline established before any research (read first, per the run's own instructions)

- `README.md`, `AGENTS.md` — product identity ("Kinetic Scientific Instrument"), frozen V1 scope, the physics/animation/UI/native architecture boundary, and explicit anti-generic-dashboard language.
- `docs/ASTRA_SKILL_MATRIX_V1.md` — the project's own pre-existing 27-category internal competency/ownership matrix. This is the single most important piece of context found: MDL already has a bespoke ownership model for design/physics/animation/testing/desktop work, but none of it is packaged as an invocable Agent Skill (no `SKILL.md`, nothing under `.claude/skills/`). The gap this run closes is wiring that existing knowledge (plus genuinely new public-skill capability) into the Skill system, not inventing a competency model from nothing.
- `docs/VISUAL_EXPERIENCE_R2_RENDERER_DECISION.md` — SVG is the production renderer; Three.js exists only as a scored, source-owned prototype boundary (`src/visualization/RendererStudy.tsx`), promotable only after a Tauri/WebView2 GPU gate. This directly shaped the scope and content of `mdl-threejs-scientific-viewport`.
- `docs/PEDAGOGY_R1_LESSON_MODEL.md` and `docs/PEDAGOGY_R1_MISCONCEPTIONS.md` — a already-implemented QUESTION/PREDICT/EXPERIMENT/OBSERVE/EXPLAIN/EQUATION/CHECK/CONTINUE lesson grammar and a concrete misconception table. `mdl-pedagogy` was written to extend this exact grammar, not to introduce a competing one (the brief's own suggested "phenomenon -> prediction -> interaction -> observation -> equation -> derivation -> interpretation" is treated as a compatible restatement, not a second model).
- `docs/VISUAL_EXPERIENCE_R2_TEST_MATRIX.md` — the existing screenshot/state matrix (13 workspaces, 900x680/1440x900/maximized, dark/light, reduced motion) that `mdl-visual-qa` wraps.
- `src/app/tokens.css` — the existing design-token system, including physically-meaningful color tokens (`--displacement`, `--velocity`, `--force`, `--energy`, `--mode-1`, `--mode-2`), which grounds `mdl-scientific-visualization`'s color-semantics section.
- `src/visualization/RendererStudy.tsx`, `src/visualization/PhysicsStage.tsx`, `src/components/EquationDerivation.tsx` — read in full to confirm the actual `PhysicalSelection` type, the `data-token` FLIP-animation convention, and the Three.js disposal/clock-subscription pattern already in production, so the custom skills describe what exists rather than inventing new conventions.
- `src-tauri/tauri.conf.json`, `src-tauri/capabilities/main.json` — confirmed an already-minimal, least-privilege Tauri configuration (window-focus events only; no filesystem/shell/network capability; a locked-down CSP). This raised the bar for what the Tauri skill selection needed to respect: nothing installed should imply widening this without justification.
- `package.json` — confirms actual dependency versions used for compatibility checks below (React 19, Three.js 0.180.0, Tauri 2, Vite 7, Playwright 1.55, `@axe-core/playwright` already present).

## 3. Per-repository findings

### anthropics/skills

`frontend-design` (24 KB) is a single, carefully written `SKILL.md` (no bundled scripts) focused on aesthetic-authorship discipline: a named list of "AI-generated design" tells to avoid (cream+terracotta palettes, SaaS-card kits, ALL-CAPS eyebrow labels, decorative numbered markers), a two-pass plan-then-build process, and explicit writing/copy guidance. No shell commands, no network calls, no destructive operations — pure instructional content. Directly useful for MDL's own "must not become a generic AI dashboard" mandate (`AGENTS.md` section 12), and treated as the project's design-authorship lead.

`skill-creator` (268 KB, mostly HTML/CSS assets for its eval viewer) is Anthropic's own meta-tool for creating and iteratively evaluating skills, including three Python scripts that call `subprocess` — every call is to `claude -p` (the Claude CLI itself, for running eval loops) or to open a local webbrowser/HTTP viewer for reviewing results; no external network calls, no arbitrary shell execution, no telemetry. Installed as the meta-tool future maintainers should use to iterate the six custom `mdl-*` skills using the same progressive-disclosure method it teaches (metadata -> SKILL.md body -> bundled references, keep SKILL.md under ~500 lines).

### jakubkrehel/skills

Eleven skills total; seven installed. `better-interface` is a pure orchestrator (it "owns" nothing substantive itself — it routes to the six domain skills and consolidates one ranked verdict with a shared severity ladder and a 15-item finding cap). Each domain skill (`better-accessibility`, `better-colors`, `better-layout`, `better-typography`, `better-ui`, `better-writing`) is compact (80-160 lines), framework-agnostic by explicit design ("write every fix in the project's own idiom... never a request to adopt a different stack"), and structured as a **review/critique** tool (severity bands, `Location`/`Before`/`After`/`Why` tables, `Block`/`Approve` verdicts) rather than an authorship tool — this is a genuinely different role from `frontend-design`, not a duplicate of it. No scripts, no network calls, no shell commands anywhere in the repository. `interface-review`, `explain-interface`, `variant`, and `break` all carry `disable-model-invocation: true` (user-invoked only); `interface-review` specifically reviews a git diff/branch/PR, which this project cannot yet exercise (no `.git` in the target directory at the time of this run) — inspected and left available for a future run once the project is under version control, not installed now.

### dawitlabs/ui-skills

Ten skills, none installed. Read `design-grill` and `ui-design-principles` in full plus samples of the others. Two disqualifying findings: (1) heavy, direct overlap with the combination of `frontend-design` (authorship) + `better-interface` suite (critique) already selected, with files 3-10x longer (300-700 lines vs. jakubkrehel's 80-160) for materially the same ground; (2) a structural fit problem specific to this project — `design-grill`'s own interview literally asks "what kind of product is this: SaaS app / developer tool / consumer app / marketing site / internal tool / design system," none of which is "offline Windows desktop scientific instrument," and its worked examples are saturated with Tailwind utility classes (`text-sm sm:text-base`, `mt-4`, `text-zinc-500`) and `globals.css`/`tailwind.config.ts` lookups, while MDL uses hand-authored CSS custom properties in `src/app/tokens.css` with no Tailwind dependency anywhere in `package.json`. The knowledge inside (color theory, the 60-30-10 rule, general UI principles) is not wrong, but it is redundant with better-scoped, already-selected alternatives and not worth the translation tax. `scripts/install.sh` (a marketplace installer) was noted but never executed, since installation here is manual and cherry-picked.

### alton47/threejs-skills

Thirteen skills, six installed (`threejs-core`, `threejs-camera`, `threejs-geometry`, `threejs-materials`, `threejs-lighting`, `threejs-performance`). Each is small (8-16 KB), single-purpose, and matches the brief's own selection criteria almost one-to-one. Rejected: `threejs-animation` (built around `AnimationMixer`/GLTF/skeletal animation for imported models — MDL's motion is physics-solver-driven, not keyframe-driven, and no module loads external rigged assets), `threejs-react` (built entirely around React Three Fiber/`@react-three/drei`/`useFrame` — not a dependency anywhere in `package.json`; `RendererStudy.tsx` uses raw imperative Three.js), `threejs-shaders`/`threejs-postprocessing` (custom GLSL and bloom/DOF/AO postprocessing conflict with `AGENTS.md`'s explicit "no neon glows, no decorative motion" identity), `threejs-xr` (no VR/AR in V1 or the stated R3 scope), `threejs-audio` (no audio in scope), `threejs-loaders` (no external 3D asset pipeline; MDL's geometry is procedural), `threejs-physics` (explicitly excluded by the run's own brief: "do not select rigid-body game-physics skills as a source of modal motion").

### zebbern/claude-code-guide

A large, mostly unrelated repository (active-directory-attacks, sql-injection-testing, metasploit-framework, and dozens of other penetration-testing skills sit alongside two design-relevant ones). Only `three-best-practices` and `design-system-builder` were opened. `three-best-practices` (200 KB, almost entirely markdown reference files organized by rule prefix — `memory-`, `render-`, `drawcall-`, etc.) is a genuinely useful **performance/memory review** overlay covering disposal discipline, delta-time animation, and draw-call budgets in far more depth than alton47's `threejs-performance` alone; it adds value as a second-opinion QA layer, exactly as the brief anticipated ("consider it as REVIEW/QA rather than a competing implementation authority"), and was installed on that basis. Its frontmatter claims `three-version: 0.182.0+` while MDL pins `three@0.180.0` (`package.json`) — a minor version-drift flag recorded in its `PROVENANCE.md`; the APIs its rules reference (Scene/Camera/Renderer lifecycle, disposal, delta-time, draw calls) are stable well below that gap, so it is not blocking. `design-system-builder` (extracting a design system from reference UI screenshots) was inspected and rejected for this run: MDL has no reference screenshots to extract from right now (no Shapr3D/Fusion/etc. mockups were supplied), so there is nothing for it to operate on; it is a reasonable candidate to revisit once the CAD Experience R3 reference-study phase actually collects comparison screenshots.

### daymade/claude-code-skills

A very large (90+ skill) general-purpose catalog; only `frontend-visual-qa` was inspected, in full (533-line `SKILL.md` plus a 2238-line `scripts/visual_layout_audit.mjs` and a smaller `silent_degradation_probe.mjs`). Security review of both scripts found no `exec`/`spawn`/`child_process` calls, no arbitrary shell execution, and no hidden network behavior beyond the Playwright-driven browsing of whatever URL the invoking user supplies (the only `process.env` reads are standard Playwright browser-path lookups for Chrome/Edge). The content quality is genuinely high — it is the most rigorously engineered of everything reviewed, with an explicit evidence-level ladder (A: real browser journey, through D: source/static reasoning) and hard rules against treating an unopened screenshot as evidence. It was not installed because its entire operating model assumes a **deployed, authenticated, multi-environment web product** (canonical URLs, environment identity, login/session flows, delivery/freshness proofs, Electron-shell chrome) that does not describe MDL: an offline, single-window, unauthenticated Tauri desktop app with no deployment target beyond the packaged installer. Installing it whole would mean carrying a large amount of dead machinery (auth-trap references, deployment-identity chains, print/PDF/download journeys) for a product that has none of those surfaces yet. Its genuinely useful ideas — "a visible signifier is not proof of behavior," the verified/partial/blocked reporting discipline, capturing evidence before and after a fix with matching crop windows — were folded into `mdl-visual-qa`'s design as inspiration, not copied as code or text.

### humbleteam/design-review

A single-skill repository (`SKILL.md` + one `references/review-rubric.md`), no scripts. Structurally the opposite of `better-interface`: a scored (0-4), citation-anchored (Nielsen heuristic number, WCAG success criterion, or named platform guideline), capped-at-6-findings critique with explicit review/comparison/advisory/grounded-advisory modes. Installed as an independent second-opinion gate, deliberately not chained to `better-interface` so the two do not groupthink on the same finding set — exactly the "independent critique... not an implementation controller" role the brief anticipated.

### pinkpixel-dev/tauri-skills

53 skills; 8 installed. Every skill file is compact (69-93 lines) and cites real `https://v2.tauri.app/...` documentation pages. A significant, honestly-reported quality finding: 50 of the 53 `SKILL.md` files (including all 8 installed here) contain an identical, generic, partly-Chinese-language filler block ("常见陷阱 / Gotchas" listing version-compatibility/config-format/env-var/dependency-conflict/performance boilerplate that applies to literally any software project, and a five-step "使用流程" — environment setup, config init, core feature use, testing, deployment — equally generic) that is not specific to Tauri at all and reads as templated padding rather than authored guidance. This does not indicate malicious content (nothing executable, no network calls, no destructive operations anywhere in the repository outside one unrelated audit script in the non-installed `tauri-app-builder` skill, which was also checked and found clean), but it lowers the instruction-quality score recorded in the scoring matrix and is called out explicitly in each installed skill's `PROVENANCE.md` so a future reader disregards that block as noise. Separately, every installed skill's frontmatter claims `license: Complete terms in LICENSE.txt`, but the source repository does not actually ship a `LICENSE.txt` inside any individual skill folder — only at the repository root (Apache-2.0). This dangling reference was resolved by copying the root `LICENSE` into each installed skill folder as `LICENSE.txt`, recorded as a relocation, not a fabrication, in each `PROVENANCE.md`. 45 of the 53 skills (mobile/plugin skills: biometric, NFC, barcode scanner, geolocation, single-instance, updater, system tray, SQL, stronghold, WASM, sidecar, etc.) were not installed because none map to a stated V1 or R3 desktop requirement.
